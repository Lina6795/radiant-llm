# S11-E 理解轨讲义：受控链聊天前端（control-chat-static）

> 范围：S11-E。新增面向用户的受控链聊天页 `app/control-chat-static/`，并在 `app/api.py` 挂载、在 Dashboard 导航加入口；不改任何后端逻辑、不改 frontend-dist。
> 现状验证日期：2026-09-29
> 读者：后续维护者与面试官。回答的问题是——**为什么聊天页必须长在 /runs + SSE 上，而不是复用旧链？**

---

## 1. 人话摘要

仓库里此前有两个前端：`app/frontend-dist/`（编译产物，旧链）和 `app/dashboard-static/`（运维界面）。S11-E 新增第三个：`app/control-chat-static/`——第一个真正面向最终用户的受控链聊天页。它只做一件事：把用户提问交给 `POST /runs`，用 SSE 事件流实时展示 search→inspect→context→draft→verify 五个节点的执行过程，最后把 verify 节点的答案、claim 判定和证据引用渲染出来。路由器拒绝（run_id 为 null）时，页面如实展示 action 和 reason_codes，并明确提示「该请求未进入受控工具链」，**绝不静默回退到旧链**。

---

## 2. 为什么不改 frontend-dist

`app/frontend-dist/` 是 React 应用的**编译产物**（压缩后的 JS/CSS），不是源码：

- **无源码可改**：仓库里没有对应的 src/，改压缩产物等于手写 minified JS，无法维护、无法评审。
- **旧链语义**：它服务的是同步 `/query`/`/stream-query` 旧链，请求-响应一次性完成，没有 run 概念、没有事件流、没有 review 队列联动。在旧链 UI 上「嫁接」受控链，等于把两套语义缝在一起。
- **构建依赖红线**：任务要求新前端为零依赖的原生 HTML/CSS/JS，引入 Node/Vite 构建链会污染交付物。

因此正确做法是新建独立目录，复用 dashboard-static 的挂载模式（RedirectResponse + StaticFiles mount），与旧产物完全隔离。

---

## 3. /runs 与 /query 的区别，以及为什么聊天页选 /runs + SSE

| 维度 | `/query`（旧链，同步） | `/runs`（受控链，异步持久化） |
| --- | --- | --- |
| 执行模型 | 请求内同步跑完，一次性返回 | 202 立即返回 run_id，后台 DurableRunner 执行 |
| 状态持久化 | 无，断开即丢 | Checkpoint + 追加式 EventStore，可恢复 |
| 过程可观测 | 无（或私有流式协议） | SSE 回放/尾随统一事件日志，支持 Last-Event-ID 续传 |
| 人工介入 | 无 | waiting_review 暂停，审核后 resume |
| 取消/恢复 | 无 | cancel / resume 一等公民 |
| 与 review 队列一致性 | 无关 | 与 Dashboard 的 Reviews 共用同一控制面 |

聊天页选 `/runs + SSE` 的三条理由：

1. **可恢复**：浏览器刷新、网络闪断后，凭 run_id 重新拉快照 + 从 seq=0（或 Last-Event-ID）重放事件流，界面状态完整重建。
2. **可观测**：五个节点的 pending/running/retry/failed/waiting_review 全部由事件驱动，时间线就是审计日志的投影，不是前端臆测。
3. **与 review 队列一致**：高风险步骤进入 waiting_review 时，聊天页给出的「前往审核」链接指向 `/dashboard/#reviews`——用户、审核员看到的是同一份 run 状态，不存在两套事实。

```
┌──────────────────────────┐
│ 浏览器 control-chat      │
│  index.html/app.js       │
│  (原生 DOM API, 无构建)   │
└─────┬───────────▲────────┘

      ▼           │
┌─────────────────┴────────┐

│  GET  /runs/{id}         │── CheckpointStore 快照
│  GET  /runs/{id}/events  │── EventStore.stream(after_seq) 轮询产出 SSE
│  POST /runs/{id}/cancel  │
│  POST /runs/{id}/resume  │
│  GET  /evidence/{id}     │──────────────┐
└─────┬────────────────────┘              │
      │ 后台线程                           ▼
      ▼                           ┌────────────────┐
┌──────────────┐  append          │ Evidence Store │
│ DurableRunner│─────────────────▶│ (evidence.db)  │
│ s1 search    │  EventStore      │ get_evidence() │
│ s2 inspect   │  (durable.db,    └────────────────┘
```

异常分支：

- **路由器拒绝**：`POST /runs` 返回 `{run_id: null, status: <action>, reason_codes}`。页面展示路由结果区（action + reason_codes + 「该请求未进入受控工具链」），不创建 EventSource、不调用任何其他查询端点。
- **waiting_review**：事件 `waiting_review` 把对应节点染黄，run 徽标转 waiting_review，显示「前往审核」链接 `/dashboard/#reviews`；审核后 `POST /runs/{id}/resume`，页面重连 SSE 继续尾随。
- **断线**：浏览器 EventSource 自动带 Last-Event-ID 重连；切换 run 或终态时前端主动 close 旧连接，避免多流并存。

## 6. 安全与健壮性红线（测试固化）

- 所有服务端文本只经 `textContent` / `createTextNode` 进入 DOM；`app.js` 与 `index.html` 全文不出现 `innerHTML`（测试直接 grep），`index.html` 无任何内联事件处理器（`on*=` 正则断言）。含 `<script>` 的恶意 claim 文本只会渲染为文字。
- 所有 fetch 走统一 `api()` 包装：网络错误、4xx/5xx、JSON 解析失败都落到状态条。
- 代码中不出现 `/stream-query`、不出现 `convchain`——没有旧链回退路径，这是产品语义而不是实现细节：路由器说「不进链」，前端就必须如实呈现，不能偷偷给答案。
