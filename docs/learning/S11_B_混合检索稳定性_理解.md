# S11-B 理解轨讲义：混合检索管线的数据流、确定性保障与 BL-T05 召回缺陷

> 范围：S11-B（T1 讲义）。只写文档，不改任何代码、不提交。
> 现状验证日期：2026-09-29
> 事实来源：管线行为与 BL-T05 根因已由诊断代理核实并经本讲义作者按行号复核，直接采用，不做重复调查。
> 读者：后续维护者与面试官。回答的问题是——**混合检索管线到底怎么流？凭什么说它是确定性的？BL-T05 的 fail 是什么性质？**

---

## 1. 人话摘要

检索管线是「两路召回 → 融合 → 过滤 → 代理重排 → 门控 → 评分」的七段流水线，生产配置是 preset `A4_gates`。整条链路**没有任何随机源**：每个排序环节都有带稳定二级键的排序键，SQL 查询带 `ORDER BY`，没有 set 迭代、没有 `os.listdir` 参与排序。S11-B 新增了端到端重复性测试（tests/retrieval/test_repeatability.py）和全阶段 per-record trace，把「确定性」从口头声明变成了可回归验证的事实。

两条遗留事实的定性：

- RET-N01 recall 0.2 → 0.1 是**语料版本漂移**（v1 → v3 摄取），不是不确定性；S11-A 已用语料内容哈希指纹堵住这类误报。
- BL-T05 是**稳定的真实召回缺陷**：gold 在库里、可达，但 BM25 和 dense 两路都召不回。保留 fail，不删、不改 skip、不硬编码绕过。

## 2. 管线数据流

入口是 `RetrievalPipeline.run`（app/retrieval/pipeline.py:101-167），每个阶段都往结构化 trace 里记账：

```
                 ┌──────────────────────────────────────────────┐
                 │                  query                       │
                 └──────────────────────┬───────────────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              ▼                                                   ▼
      ┌───────────────┐                                   ┌───────────────┐
      │  BM25 lane    │  top_k=20                         │  Dense lane   │  k=20
      │  bm25.py      │  词法匹配                          │  dense.py     │  向量近邻
      └───────┬───────┘                                   └───────┬───────┘
              │  Candidate[]  (-score, evidence_id)               │
              └─────────────────────────┬─────────────────────────┘
                                        ▼
                              ┌───────────────────┐
                              │   RRF fusion      │  score += 1/(60+rank)
                              │   fusion.py       │  合并去重、保留各 lane 原始排名
                              └─────────┬─────────┘
                                        ▼
                              ┌───────────────────┐
                              │ metadata/ACL/     │  workspace / version /
                              │ version filters   │  authority / modality /
                              │ filters.py        │  as_of / degraded；保序
                              └─────────┬─────────┘
                                        ▼
                              ┌───────────────────┐
                              │  proxy rerank     │  TokenOverlapReranker
                              │  rerank.py        │  只重排 head top_n=20
                              └─────────┬─────────┘
                                        ▼
                              ┌───────────────────┐
                              │ relevance gate +  │  低分淘汰 +
                              │ anchor gate       │  anchor 位置保护
                              │ gate.py           │
                              └─────────┬─────────┘
                                        ▼
                              ┌───────────────────┐
                              │  grader           │  充分性判定
                              │  grader.py        │
                              └─────────┬─────────┘
                                        ▼
                                  final top-20
```

生产 preset `A4_gates`（pipeline.py:202-207）= RRF k=60 + token-overlap proxy rerank top_n=20 + relevance gate min_score_ratio=0.05 + anchor gate protect_top_k=5。A0–A3 是消融阶梯（pipeline.py:184-208），逐级打开融合、重排、门控。

## 3. 确定性论证：逐环节的输入、输出与排序键

这是本讲义的重点。结论先行：**给定同一语料与同一配置，输出必然位级一致**。依据是逐环节排查，每个可能的非确定源都被堵死。

### 3.1 BM25 lane（app/retrieval/bm25.py）

- 输入：query 文本 + `load_text_evidence` 拉取的证据行。`current_only=True` 是默认（bm25.py:20,35），被取代的历史版本永不进索引；底层 store 查询带 `ORDER BY document_id, page, evidence_id`（app/evidence/store.py:307）——**语料行的枚举顺序本身确定**。
- 处理：`rank_bm25.BM25Okapi` 纯算术打分，无随机。
- 输出：top_k=20 个 Candidate。排序键 `(-score, evidence_id)`（bm25.py:84-85）——**分数并列时有稳定二级键**，不会受 `self._items` 列表顺序的偶然影响。

### 3.2 Dense lane（app/retrieval/dense.py）

- 输入：同一 query；本地 BAAI/bge-base-en-v1.5 embedding，CPU 推理，**无采样、无 seed 需求**（temperature 概念不存在于向量检索）。
- 处理：`langchain_chroma.similarity_search_with_score`（dense.py:86-104），Chroma 返回 L2 距离，单调变换为相似度，排名不变。
- chunk_id → evidence_id 映射每次运行从 `items` 重建（dense.py:29-43），而 items 的顺序由 3.1 的 `ORDER BY` 保证——映射表构建顺序也是确定的。
- 映射不上的 hit 不静默丢弃，标 `unmapped:<chunk_id>` 留在结果里（dense.py:107-110）。

### 3.3 RRF 融合（app/retrieval/fusion.py）

- 规则：`score += 1.0 / (k + rank)`，k=60（fusion.py:89）；同一 evidence_id 在两条 lane 出现时合并为一条，`source_ranks` 保留各 lane 原始排名（fusion.py:90）。
- 排序键 `(-score, best_src_rank, evidence_id)`（fusion.py:100-103）：RRF 分数并列时先比「在任一 lane 的最好名次」，再比 evidence_id——三级键，彻底消歧。

### 3.4 Metadata/ACL/Version filters（app/retrieval/filters.py:60-83）

- 检查项：workspace、document_version、authority、modality、as_of 有效期（valid_from/valid_to）、degraded。
- **保序过滤**：只删不重排（filters.py:65,81-82），kept 序列的相对顺序 = 输入顺序。
- 每条 dropped 记录 evidence_id + rank_before_filter + reasons（filters.py:74-78），可审计。

### 3.5 Proxy rerank（app/retrieval/rerank.py）

- **诚实声明：没有 Cross-Encoder**（ADR-0004）。`TokenOverlapReranker` 是确定性代理（rerank.py:7-12,37-71）：IDF 从候选内容本身估计，无 I/O、无模型、无随机。接口仿 Cross-Encoder，真模型可插在同一 Protocol 后面，但本仓库不捆绑。
- 只重排 head top_n=20，尾部保持原序；排序键 `(-proxy, pre_rerank_rank, evidence_id)`（rerank.py:102-105），pre-rerank 名次存在 `source_ranks['pre_rerank']` 里。

### 3.6 Relevance / Anchor gate（app/retrieval/gate.py）

- relevance gate 按 `min_score_ratio` 淘汰低分，不引入排序变化。
- authority 加权后如有分数变化，按 `(-score, rank, evidence_id)` 重排（gate.py:136-137）。
- anchor gate **只做位置交换**（gate.py:141-165）：把窗口外命中 anchor 的候选与窗口内最后的非 anchor 候选对调，不产生新排序、不产生随机。

### 3.7 全链路负向排查

无 set 迭代参与排序、无 `os.listdir`、无无 `ORDER BY` 的 SQL 进入排序路径。回归测试：

- 既有：tests/retrieval/test_fusion.py:33（RRF tie-break）、tests/retrieval/test_rerank_and_mapping.py:38（rerank tie-break）。
- S11-B 新增 tests/retrieval/test_repeatability.py，在真实冻结语料（M0 baseline 产物）上验证三点：
  1. 同一 pipeline 连跑 3 次，各阶段 evidence_id 序列签名一致（test_repeatability.py:70-75）；
  2. 索引与 store 从零独立重建两次，签名仍一致——专抓构建顺序/文件系统顺序/映射表的非确定（test_repeatability.py:78-84）；
  3. 每个阶段 trace 的 per-record 字段完整（evidence_id/score/rank/source_ranks，test_repeatability.py:87-100）。
  该测试在 baseline 产物缺失时 skip 而不 fail（test_repeatability.py:19-21）。

## 4. RET-N01 为什么 0.2 → 0.1：语料版本漂移，不是不确定性

- M8 baseline 跑于 2026-09-22 10:57，当时 evidence.db 只有 **v1 摄取**（valid_from=2026-09-22T03:27:32）。
- S10 跑时以 `current_only=True` 读到的是 **v3 摄取**（valid_from=2026-09-23T12:22:20）——同一 PDF 重新解析，evidence_id 全变、chunk 文本略变。
- RET-N01 的 gold 在 page 5，共 10 个 chunk：v1 时第 2 个 page-5 chunk 排第 15 名，v3 掉出 top-20 → 命中数 2/10 变 1/10 → recall@20 0.2 → 0.1。
- RET-T04 反向受益 0.2307 → 0.3077。净漂移 −0.000991。有升有降是「语料换了」的典型指纹，不是抖动。

处置（已在 S11-A 落地）：`app/eval/fingerprint.py` 增加 `_evidence_store_digest`（fingerprint.py:155）与 `_vector_store_digest`（fingerprint.py:184），语料内容哈希进指纹；Gate 对语料不一致的报告对输出 `baseline_incompatible` 而不是退化红灯。M8 基线不再用于同口径比较，S11-D 将基于 v3 语料建立新基线。

## 5. BL-T05：稳定的真实召回缺陷（保留 fail，不删不改）

Case：benchmarks/baseline_cases.jsonl 的 BL-T05，问题 "Which two English machine translation tasks are used for evaluation?"，gold anchor 在 page 6（WMT 2014 English-German / English-French 段落）。

### 5.1 gold 在库里、可达

evidence.db 中有 13 条 current、degraded=0、modality=text、page=6 的行（document_id=e8a365c1d8815226）。只读验证（实测返回 `0|text|13`）：

```bash
sqlite3 "file:artifacts/baseline/m0-20260922/evidence.db?mode=ro" \
  "SELECT degraded, modality, COUNT(*) FROM evidence \
   WHERE document_id='e8a365c1d8815226' AND page=6 AND valid_to IS NULL GROUP BY 1,2"
```

### 5.2 但两路召回都漏了它

M8 与 S10 两次运行中，BM25 和 dense **都没有**把任何 page-6 chunk 召回进 28 条融合池：trace 里 `anchor_protection=[]`，filters 阶段无 drop——anchor gate 根本无料可提。所以：

- 不是 gold 不可达（5.1 已证可达）；
- 不是被过滤器误删（dropped 里没有 page-6 记录）；
- 不是抖动（两次运行、两种语料版本一致 fail，不贡献漂移）；
- 是两路召回对「Which two English machine translation tasks…」这种问法都失效的**真实质量缺口**，稳定复现。

### 5.3 处置

按 S11 规则：**保留 fail 并记录于此，不删 case、不改 skip、不在管线里硬编码绕过**。后续修复方向（仅记述，不在本期实施）：查询扩展 / 多路召回，或对 page-6 的 token 分布做针对性分析，弄清为什么 BM25 的词面匹配与 dense 的语义匹配同时错过该段。

## 6. S11-B 新增的可审计性

- pipeline trace 每个阶段（recall_bm25 / recall_dense / fusion / rerank）新增 `top_k` 字段（pipeline.py:34-37,93,104,135,156）：每条记录携带 evidence_id / score / rank / source / source_ranks / filter_reasons / gate_notes（字段由 `Candidate.to_trace` 定义，app/retrieval/types.py:44-60）。
- filters 阶段保留完整 `dropped`（evidence_id + rank_before_filter + reasons，pipeline.py:140-145）；gates 阶段保留 `relevance_dropped` 与 `anchor_protection`（pipeline.py:163-169）；`final` 保留完整 to_trace（pipeline.py:175）。
- eval 的每 case artifact（`artifacts/eval/<run>/retrieval/<dataset>/<case_id>.json`）自动携带全部阶段 trace——逐 case 归因不再需要手工重跑管线。

---

## 7. 一句话记住本讲义

> 这条管线的确定性不是「测出来没发现问题」，而是每个排序键都有 evidence_id 兜底、每处枚举都有 ORDER BY 撑腰；RET-N01 的漂移是换了题库，BL-T05 的 fail 是真召回漏洞——前者靠指纹封口，后者留着当证据，都不靠祈祷。
